What actually happens
when you open a website?

The Pi carries the traffic in both directions. Linux forwards the website’s encrypted packets. Our Go/PocketBase backend watches metadata alongside that traffic and builds the dashboard.

Does the reply go “directly” to the phone? It goes directly to the phone’s browser connection, through the Pi’s network stack. It does not bypass the Pi, and it does not need Go/PocketBase to read, store, or relay the page.

Gateway = the whole Pi

Runs Wi-Fi, DHCP, DNS, Linux routing/NAT, the observers and PocketBase. Website packets physically traverse this machine.

Backend = the Go application

Reads observations, derives labels, runs background probes and serves the dashboard API. Normal web connections are not opened or terminated by this application.

Follow a single visit

From joining Wi-Fi to seeing the page

Example: a phone uses the default IPv4 gateway, classic DNS, and HTTPS. The lab gate is off. This explains the checked-out code; it is not a captured SVT visit. Actual SVT IPs, redirects and resources can vary.

1

The phone joins “Infrareveal”

hostapd provides Wi-Fi. dnsmasq gives the phone a local IP, for example 10.0.0.50, with the Pi at 10.0.0.1 as its gateway and DNS server.

Phone⇄Pi: Wi-Fi + DHCP

The configured address pool is 10.0.0.50–150, with 12-hour leases. DHCP is local setup traffic; it is not saved as a website flow. dnsmasq also writes DHCP service logs.

2

The phone asks: “What IP is svt.se?”

If it needs a DNS lookup, the phone asks the Pi. IPv4 TCP/UDP port 53 traffic from the Wi-Fi interface is redirected to local dnsmasq, even if the phone addresses another classic DNS server.

Phone⇄Pi: dnsmasq⇄Upstream DNS, if uncached

dnsmasq answers from its cache or asks upstream. The config adds Google DNS at 8.8.8.8; it does not disable system-configured resolvers. The answer returns to dnsmasq, then to the phone.

LoggedGo tails /var/log/dnsmasq.log and saves the client IP, queried name/type, observed time, answers and alias information in dns_queries. Saving the record is not a prerequisite for returning the DNS answer.

If the name is already cached, or DNS is encrypted

A phone/browser cache hit can skip DNS entirely. A dnsmasq cache hit skips only the upstream query; the local query can still be logged.

DNS-over-HTTPS or DNS-over-TLS does not use this plain port-53 path. It is forwarded as encrypted traffic. The backend may see the resolver connection, but not the names requested inside it.

A DNS request can ask for IPv4 addresses (A), IPv6 addresses (AAAA), or other record types. Receiving an AAAA answer does not mean this deployment provides IPv6 internet routing; the supplied forwarding rules and default observation scope are IPv4.

3

The phone connects to the returned IP

The phone starts an HTTPS connection: commonly TCP port 443 + TLS, or QUIC over UDP port 443. Linux forwards the packets from wlan0 to eth0.

Phone → destination IP:443→Pi: NAT→SVT / CDN

NAT replaces the phone’s private source address with the Pi’s uplink address and remembers the mapping. The upstream router may perform another NAT. The server replies toward that outward-facing address; Linux uses the mapping to deliver replies to the right phone.

LoggedThe backend samples Linux’s connection table (conntrack) about once per second: who connected to which IP and port, protocol, state, packet counts and byte totals in both directions.

4

The browser requests the page inside encryption

The phone and the website establish the secure connection. The browser sends the HTTPS request through it. The Pi forwards encrypted packets; it does not install a client certificate, decrypt TLS, or choose an upstream server using the TLS hostname (SNI).

Phone: encrypt request→Pi: forward packets→Server: decrypt request

The URL path, query string, HTTP headers, cookies and request body stay inside HTTPS. DNS may reveal svt.se; it does not reveal which article the user requests.

5

The page comes back through the Pi

The server sends the encrypted response. The Pi forwards it to the phone using the connection/NAT mapping. The phone decrypts the response and renders the page.

SVT / CDN→Pi: reverse NAT + forward→Phone: decrypt + render

LoggedA passive packet observer on wlan0 also counts traffic in both directions, grouped into 50 ms time buckets. It stores lengths, counts and flags, not the returned HTML or images.

6

The browser fetches the rest of the page

Images, scripts, fonts and video can need more requests, DNS lookups and connections. Some reuse the existing connection; some contact other hosts; some come from the phone’s cache. These actions can overlap while the page is already appearing.

HTML+Images / styles / scripts→Page on your phone

One recorded flow is a network connection, not one page or one file. Several resources can share a connection. InfraReveal cannot determine the browser’s exact “page finished loading” moment from this metadata.

Alongside the page load

What else does our backend look up?

These tasks enrich the dashboard after observations arrive. The phone does not wait for their results. Some create separate network traffic from the Pi.

Local database match

“Which hostname fits this IP?”

Saved DNS answers + saved flow → candidate name

About every 3 seconds, the correlator checks the same client’s DNS answers against the flow’s destination IP. It chooses the closest qualifying answer around the flow’s observed start, normally within the preceding 5 minutes.

A match becomes a medium-confidence hostname such as svt.se. No new DNS request is needed. Shared IPs and caching make this an inference.

Separate network lookup

“Does this IP have a reverse name?”

Pi ⇄ its configured DNS resolver

A reverse-DNS (PTR) lookup asks for a name attached to the destination IP. It uses Go’s default/system resolver, has a 500 ms timeout, and is eligible for refresh after 15 minutes.

The reply belongs to the Pi’s own lookup. It enriches destinations; it is not the website response and is not delivered to the phone.

Local data lookup

“Where is this IP, and who runs it?”

IP → local GeoIP database + provider rules

If available, the local GeoIP database supplies approximate city, country and coordinates. Provider labels come from reverse-name heuristics or known-network rules.

This code does not call an external GeoIP or WHOIS API. A label or map location is context, not proof of the website owner or a server’s exact physical location.

Separate probe traffic

“Which routers answer on the way?”

Pi ⇄ routers / destination

The route worker checks its cache, then sends bounded traceroute probes if needed. Fast probes use the observed destination IP, protocol and port; later coverage attempts can use other probe methods.

Probe replies terminate at the Pi. They never become the phone’s page data. A trace approximates a route from the gateway; it does not prove the website packets’ exact path or measure their return path.

The two DNS lookups answer different questions. The phone’s forward lookup asks “where is svt.se?” so it can connect. The Pi’s optional reverse lookup asks “what name is attached to this IP?” to label the dashboard.

Exactly what the packet observer touches, stores and misses

Linux AF_PACKET provides a passive copy of a bounded packet prefix on the Wi-Fi interface. A BPF filter caps each captured prefix at 256 bytes. That prefix can include some payload bytes beyond the headers; the parser reads network/transport headers and retains only derived metadata. It does not save packet bodies or a packet capture file.

The observer uses the original frame length and header lengths to calculate traffic sizes. The web payload itself is encrypted in this example. It does not extract URLs, cookies, HTML or TLS hostnames.

Activity is attached to a matching stored flow. Packets that cannot be parsed or matched do not produce a complete resource-level history. Capture windows/status records track availability, drops, errors and unmatched events. A gap does not prove that the phone was idle.

Default detailed-activity retention is 24 hours for inactive sessions; this is not a blanket 24-hour deletion policy for every metadata collection. PocketBase data persists through the Compose ./data volume. The dnsmasq text log is a separate service log.

Only client-initiated public-destination traffic within the configured observation scope becomes a website flow. Gateway-generated probes and local/infrastructure traffic such as classic DNS, DHCP, NTP, mDNS and the conventional UDP traceroute range are excluded. DNS has its own collection.

Exact hostname-matching and grouping rules

The matcher considers DNS records in the same session, requires the same client IP and a matching destination IP in the answers, and chooses the nearest eligible timestamp to the flow’s observed start. The window is 5 minutes, with up to 10 seconds of later DNS timing tolerated. This is a fixed matching window, not a stored DNS-TTL check.

Without a DNS match, known reduced-visibility ports produce a hidden label; other flows remain low confidence with only their destination IP. A port-based label is a heuristic, not confirmation of a specific VPN or encrypted DNS product.

Usable high/medium-confidence names group by registered domain and the explicit alias table. The same client’s www.svt.se and svtstatic.se can therefore appear under svt.se. Original endpoint names remain visible. Timing, shared providers and CNAME chains do not by themselves merge different domain groups. Unresolved traffic remains independent.

What the picture can and cannot say

We can show connections. We cannot replay the webpage.

Visible: endpoints, timing and volume

We observe IPs, ports, protocols, counts and timings. Local DNS can supply candidate hostnames. The flow list includes other apps’ traffic too, not just the browser.

Hidden inside HTTPS: the content

We do not decrypt or store article paths, query strings, cookies, form contents, HTML, images or video. The phone and the remote HTTPS endpoint handle that content.

Encrypted DNS / VPN / Private Relay

Hostname evidence can disappear. A tunnel can leave us seeing only the tunnel or relay endpoint and its traffic volume, not the websites inside.

The map is an approximation

Route probes are separate packets; internet routes can differ in each direction. Drawing incoming traffic along a measured route does not mean we measured the return route.

The exception: explicitly armed Proxy Lab

Everything above describes the default passive mode. LAB_GATE_ENABLED is false by default. Enabling support alone still does not hold client traffic.

What changes when an operator arms the gate?

An authenticated operator selects IPv4 clients in an active session. Linux NFQUEUE then holds selected packets while the Go gate decides when to accept or drop them. Here, selected traffic really does wait for a backend verdict before forwarding or local DNS delivery.

  • Flow mode: holds admission of new TCP/UDP flows.
  • Strict mode: steps packets for one exact connection tuple in both directions.
  • DNS mode: gates selected traffic going to local dnsmasq.

Accepted traffic continues through the normal network path. This still does not decrypt HTTPS. Timeouts and fail-open behavior limit stalls. Gate decisions have a separate audit trail in gate_events.

DEBUG_TRACE_ENABLED is another, independent option: bounded in-memory metadata events streamed to the debug dashboard. Passive tracing alone does not hold packets.

The shortest explanation

The phone asks for an address, then talks securely to the website through our Pi. The Pi forwards both directions. Our backend records connection metadata and visible DNS, then adds inferred names and approximate routes. The phone receives, decrypts and displays the page.
