# Mapping the Path Your Internet Traffic Actually Takes

## The core idea: traceroute is an inference, not a packet flight recorder

Your current approach is directionally right, but it mixes together several different things that look like “the route” while actually answering different questions.

A useful way to think about the problem is that there are at least four distinct paths you might want to reconstruct:

| Layer | What you are really trying to learn | How observable it is from your client |
|---|---|---|
| **Application endpoint** | Which IP address and protocol your browser actually connected to | Very observable |
| **IP forwarding path** | Which Layer-3 routers/interfaces forwarded that particular flow | Partially observable |
| **AS/network path** | Which ISPs, transit networks, peers, and destination networks were involved | Usually fairly observable |
| **Physical path** | Which buildings, POPs, fibers, submarine cables, switches, MPLS nodes, etc. carried the bits | Often impossible to determine externally |

The most important correction to your current model is this:

> **A traceroute does not follow one real application packet and ask it which routers it crossed.**

Instead, it sends a sequence of specially constructed *new packets* and deliberately causes one packet to die at hop 1, another at hop 2, another at hop 3, and so on. It reconstructs a path from the error messages generated by routers along the way. IPv4 routers decrement the packet's TTL while forwarding; when it reaches zero, the packet is discarded and an ICMP Time Exceeded message is normally sent back to the source. citeturn20view1turn20view2

That distinction explains most of the strange behavior you are seeing.

A better mental model is:

```text
Actual HTTPS flow:

your laptop
    |
    v
home router/NAT
    |
    v
ISP access network
    |
    v
ISP core / MPLS / ECMP
    |
    v
peering / transit / IXP
    |
    v
CDN or service edge
    |
    v
application

Traceroute:

probe TTL=1  ---> dies here -------- ICMP reply ------> you
probe TTL=2  -------> dies here ---- ICMP reply ------> you
probe TTL=3  ------------> dies ---- maybe no reply
probe TTL=4  -----------------> dies maybe no reply
...
probe TTL=N  -------------------------------> destination replies
```

So when you get something like:

```text
1   192.168.1.1
2   81.x.x.x
3   *
4   *
5   *
6   *
...
13  151.x.x.x
```

it does **not** mean that traffic jumps from hop 2 directly to hop 13 or that hops 3–12 do not exist. It means traceroute received no usable response for those TTL positions. The real application traffic can be flowing through those routers perfectly normally.

In fact, the fact that the destination responds after a run of `*` proves that packets are continuing through some forwarding path beyond the silent points.

## What traceroute is actually doing on the network

### TTL is the mechanism traceroute exploits

IPv4 contains an 8-bit Time To Live field. In practical Internet forwarding, it behaves primarily as a hop limit: every router forwarding the packet reduces it by at least one. If the result reaches zero, the router discards the packet and ordinarily generates ICMP Time Exceeded back toward the sender. citeturn20view2

Suppose the real IP forwarding path were:

```text
Client -> R1 -> R2 -> R3 -> R4 -> Server
```

Traceroute effectively performs:

```text
Packet A: TTL 1
Client -> R1
          TTL becomes 0
          DROP
          ICMP Time Exceeded -> Client

Packet B: TTL 2
Client -> R1 -> R2
                TTL becomes 0
                DROP
                ICMP Time Exceeded -> Client

Packet C: TTL 3
Client -> R1 -> R2 -> R3
                      TTL becomes 0
                      DROP
                      ICMP Time Exceeded -> Client
```

and continues until a probe reaches the destination.

The traceroute program knows which TTL it gave each probe, measures the elapsed time until a corresponding response arrives, and associates the source IP of that response with that TTL.

There is no accumulation such as:

```text
packet.route = [router1, router2, router3, ...]
```

inside a normal IP packet.

Traceroute is therefore better described as **active tomography**: infer internal structure by stimulating the network and observing responses.

### Different traceroute implementations send different kinds of probes

This matters much more than it first appears.

Windows `tracert`, for example, uses ICMP Echo Request packets with successively increasing TTL values. Microsoft's documentation explicitly notes that some routers do not send Time Exceeded responses and therefore appear as `*`. citeturn19view17

Other traceroute implementations commonly support UDP, ICMP, or TCP probes. Modern measurement software such as CAIDA's Scamper supports classic and Paris-style traceroute and probe methods including UDP, ICMP, and TCP. citeturn20view6turn20view7

That means these are not necessarily equivalent:

```text
ICMP traceroute -> example.com
UDP traceroute  -> example.com
TCP traceroute  -> example.com:443
actual HTTPS TCP connection -> example.com:443
actual QUIC UDP connection  -> example.com:443
```

A firewall, router ACL, or load balancer can treat them differently. Therefore, one of the best improvements you can make is to probe using traffic that resembles the application flow you actually care about.

### The IP you see for a hop is subtler than “the router's location”

Another surprisingly important problem is the IP address displayed for a traceroute hop.

An ICMP error needs a source address. Under IPv4 router requirements, that address is normally associated with the interface through which the **ICMP response is sent back**. It does not necessarily identify the forward-path interface on which your original probe arrived. RFC 5837 was specifically created because ordinary ICMP responses often do not explicitly tell you the incoming interface, outgoing forwarding interface, or next hop. citeturn21search3

Consider:

```text
                  forward probe
you -------------------------------->
                    Router X
                         \
                          \ ICMP response returns
                           \
                            <--------- via interface 203.0.113.8
```

Traceroute may display:

```text
203.0.113.8
```

You might then geolocate `203.0.113.8` and plot that as the physical point your forward traffic passed through.

That inference can be wrong.

It may merely be an address associated with Router X's return-facing interface. And one physical router can have many IP interfaces. This is one reason serious Internet-topology research performs **alias resolution** to determine when several observed IP addresses belong to the same router. CAIDA specifically treats mapping interfaces to routers as a separate topology-inference problem. citeturn22search1

### The RTT shown for hop N is not the latency of link N

Another common mapping error is to interpret:

```text
hop 5   20 ms
hop 6   70 ms
```

as:

```text
link hop5 -> hop6 = 50 ms
```

That is not necessarily true.

The measurement is approximately:

```text
RTT(hop 6) =
    time for probe from you -> router 6
    +
    time for ICMP reply from router 6 -> you
```

The ICMP response can take a different route back. Internet forward and reverse routes are frequently asymmetric because of interdomain policy, traffic engineering, load balancing, and other routing decisions. Standard traceroute measures the forward TTL-expiry sequence but does not reveal the complete reverse route taken by each response. citeturn20view12

Therefore:

```text
RTT(6) - RTT(5)
```

is at best a rough clue and is not a reliable measurement of the latency of the physical link between routers 5 and 6.

## Why you see so many missing hops

Your observation—one home hop, perhaps one ISP hop, then many stars, sometimes followed by the final destination—is entirely plausible on a healthy network.

Several independent mechanisms can produce that result.

### Routers can forward packets without answering traceroute

The forwarding plane and the control plane are separate concerns.

A router may be perfectly willing to do:

```text
incoming IP packet
      |
      v
routing lookup
      |
      v
forward at line rate
```

while being unwilling or unable to spend resources doing:

```text
construct ICMP error
route ICMP error
send it back to arbitrary Internet host
```

IPv4 router requirements specify ICMP Time Exceeded for an expired TTL, but they also permit a configurable per-interface disable. They additionally recommend rate limiting ICMP error generation. citeturn20view1turn20view0

So:

```text
* * *
```

means:

> No matching response arrived before traceroute's timeout.

It does **not** mean:

> No router forwarded the traffic.

That distinction is fundamental.

### ICMP may be filtered somewhere after it was generated

Imagine router R7 sends this:

```text
R7 -> ICMP Time Exceeded -> ... -> your ISP -> firewall -> DROP
```

Traceroute displays:

```text
7   * * *
```

even though R7 did exactly what traceroute expected.

Filtering can exist at the router itself, somewhere on the return route, or near your own network. Consequently, a silent hop does not let you distinguish between:

```text
router did not generate response
router generated it but rate-limited it
router generated it but a later ACL dropped it
response was lost through congestion
response took too long
```

from the traceroute output alone. The standards explicitly contemplate ICMP error rate limiting. citeturn20view0

If you consistently observe:

```text
1  home router
2  ISP
3  *
4  *
5  *
...
17 destination
```

for many unrelated destinations, my strongest working hypothesis would be **some shared policy, filtering behavior, or tunneling inside/near the ISP**, rather than every router on the Internet independently deciding not to answer you. That is an inference, however, not something the traceroute alone proves.

Testing ICMP, UDP, TCP/443, and IPv4 versus IPv6 separately is a good way to narrow it down.

### MPLS can deliberately hide multiple physical routers

This is a major reason that “number of traceroute hops” and “number of routers your packet physically crossed” can diverge.

Many providers transport IP packets across MPLS label-switched paths. MPLS supports different TTL models. Under the **Pipe Model**, the MPLS network can appear externally like a single hop even though packets traverse multiple label-switch routers internally. RFC 3443 explicitly defines this behavior. citeturn21search0turn21search4

For example:

```text
IP view:

A ------------ B
   appears as
   one step

physical/MPLS underlay:

A -> LSR1 -> LSR2 -> LSR3 -> LSR4 -> B
```

Your ordinary traceroute may therefore report something resembling:

```text
7  ISP ingress
8  ISP egress
```

while internally the traffic actually traversed several additional routers.

Some routers expose MPLS label-stack information in extended ICMP messages under RFC 4950, allowing enhanced traceroute implementations to show MPLS labels. Operators are also permitted to expose that information selectively. citeturn21search1turn21search5

This gives you an important boundary:

> **From outside the network, you often cannot reconstruct the exact physical underlay at all.**

No amount of ordinary traceroute probing can reveal routers whose tunnel semantics intentionally make them invisible.

### Load balancing can make ordinary traceroute invent paths that no packet took

This is perhaps traceroute's most subtle failure mode.

Routers frequently have several equal-cost next hops:

```text
                -> R2A ->
R1 -> ECMP                 -> R3
                -> R2B ->
```

They commonly choose among them based on flow-related fields such as:

```text
source IP
destination IP
protocol
source port
destination port
```

—the familiar five-tuple. Research behind Paris traceroute showed that classic traceroute may inadvertently change fields between probes that routers use for load balancing. citeturn20view4turn20view5

Suppose actual flows are:

```text
Flow A: R1 -> A -> C -> R4

Flow B: R1 -> B -> D -> R4
```

A naïve traceroute might probe TTLs using different flow identifiers and receive:

```text
TTL 2 -> A
TTL 3 -> D
```

then infer:

```text
A -> D
```

even though that link may not exist at all.

That is why simply drawing lines between successive ordinary traceroute IPs can produce a fictitious topology.

**Paris traceroute** was designed to fix this: it holds load-balancing-sensitive fields constant so the sequence of probes behaves more like one flow. Scamper now provides Paris-style traceroute directly. citeturn20view5turn20view7

There is a second question you may want to ask:

> What are *all* the potential ECMP paths, rather than the path associated with one stable flow?

For that, CAIDA Scamper provides `tracelb`, implementing the Multipath Discovery Algorithm to infer per-flow load-balanced paths with configurable confidence. citeturn20view8

These are two different measurements:

```text
Paris traceroute:
"What path would a stable flow likely see?"

MDA / tracelb:
"What set of load-balanced paths appears to exist?"
```

For your goal, you want both—but should never merge them as if every observed branch belonged to a single packet.

### Private and CGN addresses should not be geolocated

Your first hop such as:

```text
192.168.1.10
```

has no meaningful global geographic location. It is local address space.

Likewise you may encounter:

```text
10.x.x.x
172.16.x.x - 172.31.x.x
192.168.x.x

or

100.64.x.x - 100.127.x.x
```

The latter range, `100.64.0.0/10`, is Shared Address Space specifically intended for uses such as carrier-grade NAT between subscriber equipment and provider infrastructure and is not globally routable across provider boundaries. citeturn20view16

Any commercial GeoIP result that assigns a city to such an address should not be interpreted as the router's real location.

## DNS and GeoIP are not telling you the “actual final destination”

This part of your pipeline deserves almost as much revision as traceroute.

Your current logic is approximately:

```text
nytimes.com
   |
   v
DNS query
   |
   v
IP 203.x.x.x
   |
   v
GeoIP
   |
   v
"the destination is New York"
```

There are several reasons that conclusion may be wrong.

### The address from your separate DNS lookup might not be the one the application uses

Modern clients may receive multiple IPv4 and IPv6 addresses and race connection attempts. The Happy Eyeballs algorithm explicitly involves asynchronous DNS resolution, ordering candidate destination addresses, beginning connection attempts, and keeping the connection that succeeds. citeturn20view10

Modern DNS can also provide HTTPS/SVCB records that tell a client about alternative service endpoints and protocol choices; RFC 9460 specifically allows an HTTP client to select an operationally preferable endpoint and facilitate HTTP/3. citeturn20view11

So this:

```bash
dig nytimes.com
```

followed by:

```bash
traceroute <one-answer>
```

does not necessarily reproduce what the browser did.

For the path you *actually* used, the correct starting point is:

> **Observe the real connection that left your machine.**

A packet capture or OS socket-level observation should record at least:

```text
timestamp
local IP
local port
remote IP
remote port
transport protocol
IP version
```

For example:

```text
192.168.1.24:51862
    ->
203.0.113.80:443
TCP/IPv4
```

or:

```text
2001:db8:...:53121
    ->
2001:db8:abcd::80:443
UDP/IPv6
```

Then measure *that* remote IP, not whichever address a later DNS command happened to return.

This becomes particularly relevant for HTTP/3, because a service may be reached over UDP rather than TCP, and service-binding DNS can advertise protocol and endpoint alternatives. citeturn20view11

### A single IP may not correspond to a single physical destination

Anycast deliberately announces the same service address from multiple independent locations. Routing then sends traffic toward one of those nodes. RFC 4786 defines an anycast service precisely in those terms. citeturn21search2

Conceptually:

```text
                  Stockholm server
                 /
203.0.113.1 ----<
                 \
                  Frankfurt server
                 \
                  London server

same IP address
multiple physical locations
```

A GeoIP database has to represent that somehow, but there is no single objectively correct latitude/longitude for the IP itself.

What matters is:

```text
your source network
+
routing state at that moment
+
anycast catchment
=
which node received your traffic
```

A distributed measurement from a different country could hit a completely different machine while targeting exactly the same IP.

That means the geographic object you ideally want to infer is not:

```text
location(IP)
```

but rather:

```text
location(the instance of IP reached from
         source S at time T)
```

That is a much harder problem.

### City-level GeoIP should be treated as evidence, not ground truth

RIPE NCC's IPmap is instructive here because it does not pretend that IP location is a trivial database lookup. Its system combines multiple inference engines and uses active latency measurements to constrain plausible locations; RIPE explicitly describes its location score as relative rather than an accuracy probability and calls accuracy evaluation an open research area. citeturn20view15

For topology visualization, a stronger model is therefore:

```text
router/interface 203.x.x.x

ASN:          high confidence
network:      high confidence
country:      perhaps medium/high
city/POP:     evidence-dependent
coordinates:  estimate
```

rather than:

```text
203.x.x.x = exact building at 59.3293,18.0686
```

Reverse DNS names are also valuable evidence because operators often encode router or POP naming schemes, and latency constraints can help reject geographically impossible candidates. But these should remain confidence-weighted clues rather than absolute facts.

There is another complication: because the ICMP source address can identify the interface used for the reply rather than the forward ingress interface, even an *accurately* geolocated hop IP does not automatically give you the exact point you should draw on the forward-data-path map. RFC 5837 exists in part to expose this otherwise missing interface information. citeturn21search3

## Better tools for reconstructing the path

I would move from “DNS + normal traceroute + GeoIP” to a measurement stack.

### Scamper and Paris traceroute should be your primary traceroute layer

For serious path measurement, CAIDA's **Scamper** is substantially more appropriate than treating the operating system's default traceroute output as ground truth. It supports IPv4/IPv6 traceroute, Paris-style probing, multipath discovery, alias-resolution methods, and other active-measurement techniques. citeturn20view6

For a single likely per-flow path:

```bash
sudo scamper -I "trace <IP>"
```

Current Scamper documentation describes `trace` as supporting classic and Paris-style traceroute and states that it infers a single path. citeturn20view7

For a service that is actually using TCP/443, test a TCP path:

```bash
sudo scamper -I "trace -P TCP -d 443 <IP>"
```

Scamper's current trace command supports selectable probe methods and destination-port control. citeturn20view7

For something resembling UDP/443 transport, such as an HTTP/3 destination:

```bash
sudo scamper -I "trace -P UDP-Paris -d 443 <IP>"
```

The goal is not to assert that these synthetic probes are identical to browser traffic. They are still traceroute probes. The goal is to minimize needless differences in the forwarding characteristics that might influence ACLs or flow hashing.

For ECMP topology rather than one path:

```bash
sudo scamper -I "tracelb -c 99 <IP>"
```

`tracelb` uses the Multipath Discovery Algorithm to infer per-flow load-balanced paths and supports 95% or 99% confidence settings. citeturn20view8

A good conceptual output format is:

```text
                        +--> B1 --> C1 --+
A --> ISP edge ---------|                |--> D
                        +--> B2 --> C2 --+

Observed single flow: A -> edge -> B1 -> C1 -> D
Alternative ECMP path:  A -> edge -> B2 -> C2 -> D
```

Do not collapse that graph into:

```text
A -> edge -> B1 -> B2 -> C1 -> C2 -> D
```

because that path may never exist.

### MTR is useful for repeated measurements, not as a magic topology resolver

`mtr` combines traceroute-style path discovery with repeated probing. Its official repository describes it as a network diagnostic tool, and current versions support alternate transport methods including TCP and UDP. citeturn19view5

A useful test is:

```bash
mtr --tcp --port 443 --report <IP>
```

The point here is different from Paris traceroute:

```text
Scamper/Paris:
better structural inference

MTR:
how responses/RTT/loss-looking behavior evolve over repeated probes
```

One important interpretation rule: packet loss reported at an intermediate router but not propagated to later hops is usually evidence that the router is deprioritizing or rate-limiting measurement responses, not that it is dropping the corresponding fraction of forwarded user traffic. ICMP generation can be rate-limited independently of ordinary forwarding. citeturn20view0

For example:

```text
hop       apparent loss
ISP-A       0%
ISP-B      80%
ISP-C       0%
target      0%
```

does **not** make sense as “80% of packets stop at ISP-B.” If that were true, later hops would also experience that loss. It is much more consistent with ISP-B answering only some measurement probes.

### Use BGP to understand networks, not individual routers

After traceroute, map every globally routable IP to:

```text
prefix
origin ASN
organization
```

Then annotate transitions such as:

```text
home
  |
ISP AS1234
  |
Transit AS1299
  |
Destination/CDN ASxxxx
```

RouteViews exposes prefix information including origin ASN and AS paths reported by its BGP peers. citeturn22search2 RIPE RIS likewise operates route collectors at multiple locations and IXPs. citeturn20view13

But BGP needs to be interpreted correctly.

A RouteViews path such as:

```text
AS64500 -> AS1299 -> AS13335
```

means roughly:

> This RouteViews peer's BGP control-plane view learned that destination prefix with this AS-path attribute.

It does **not** mean:

> Your exact packet definitely traversed these routers in exactly this order.

A route collector is another vantage point. RouteViews itself emphasizes that its collectors are not the packet-forwarding dataplane. citeturn22search2

Therefore BGP is most useful as a **consistency and ownership layer**:

```text
traceroute says IP A -> IP B -> IP C

prefix mapping says:
A = your ISP
B = your ISP
C = destination CDN

BGP says:
your ISP has plausible path toward destination CDN

=> topology interpretation becomes stronger
```

### Use RIPE Atlas for additional vantage points

A path measured only from your laptop tells you what is observable from one source network.

RIPE Atlas can initiate traceroute measurements from selected probes by geography, ASN, or explicit probe IDs. citeturn22search0

This is especially useful for questions such as:

```text
Is this destination anycast?

Does everyone see this silent MPLS section?

Is the strange routing specific to my ISP?

Where does traffic from Stockholm vs Amsterdam vs London enter the CDN?

Does IPv6 take a different provider/path?
```

For example, imagine the same IP produces:

```text
Stockholm probe -> Stockholm edge
Amsterdam probe -> Amsterdam edge
London probe    -> London edge
```

That strongly supports a distributed/anycast service interpretation rather than “the server is located at the GeoIP coordinate.”

RIPE Atlas does not reveal your exact client path unless the measurement vantage is your own network or sufficiently representative of it. Its value is comparison and triangulation.

### Use alias resolution if you want a router-level graph

Raw traceroute produces **IP interfaces**.

Your visualization probably wants **routers**.

Those are different.

Suppose you observe:

```text
192.0.2.4
198.51.100.7
203.0.113.12
```

It is possible that all three addresses belong to one physical router:

```text
       [ Router R ]
       /    |     \
192.0.2.4  ...  203.0.113.12
```

CAIDA's topology tooling explicitly performs alias-resolution techniques to collapse multiple interfaces into routers and combines such results with traceroute and AS-level inference. citeturn22search1turn22search4

Without this step, a map can dramatically over-count “routers.”

For a production-quality topology mapper I would therefore keep separate IDs:

```text
observed_interface_ip
inferred_router_id
inferred_asn
```

rather than making `IP address == router` an assumption.

## A high-fidelity measurement workflow

The most important change is to reverse the order of operations.

Do **not** begin with:

```text
hostname -> DNS lookup -> guessed destination
```

Begin with:

```text
actual application flow -> observed destination
```

Then explain that observed flow with topology measurements.

### Capture what the application actually did

While loading the site, collect the actual network flow information from the client or gateway.

Your initial record for one connection should resemble:

```text
measurement_id:      8fa...
time:                2026-09-17T...
process/application: browser
local_address:       192.168.1.50
local_port:          54021
remote_address:      203.0.113.24
remote_port:         443
protocol:            TCP
address_family:      IPv4
```

and perhaps another:

```text
remote_address:      2001:db8:1234::50
remote_port:         443
protocol:            UDP
address_family:      IPv6
```

This avoids assuming that one independent DNS lookup reproduces the client's endpoint selection. Happy Eyeballs and modern HTTPS/SVCB behavior are exactly why that assumption is unsafe. citeturn20view10turn20view11

Also retain the DNS answers actually observed around that application session. DNS is still highly useful; it simply should not be treated as proof that one particular answer was used.

### Measure each actual remote tuple using several probe modes

For every destination address used by the real application, run something conceptually like:

```text
actual flow:
TCP / IPv4 / destination port 443

measure:
Paris UDP traceroute
TCP traceroute to port 443
MDA traceroute
repeated MTR
```

The different results themselves are data.

For example:

```text
ICMP:
1 A
2 B
3 *
4 *
5 destination

TCP/443:
1 A
2 B
3 C
4 D
5 destination
```

That tells you something highly relevant:

> The topology may be observable when probes resemble permitted application traffic, while another probe class loses visibility.

Conversely:

```text
TCP/443:
1 A
2 B
3 *
...
17 destination

UDP Paris:
1 A
2 B
3 *
...
17 destination
```

makes a tunnel or broad ICMP-response visibility policy more plausible than a UDP-only firewall explanation.

That conclusion would still be probabilistic rather than definitive.

### Run IPv4 and IPv6 independently

Do not merge them.

Treat:

```text
A record -> IPv4 graph
AAAA record -> IPv6 graph
```

as potentially unrelated topologies.

Happy Eyeballs can choose among those address families during connection establishment. citeturn20view10

Your map might legitimately show:

```text
IPv4:
Stockholm -> ISP A -> Copenhagen -> Frankfurt -> CDN

IPv6:
Stockholm -> ISP A -> Stockholm peering -> CDN
```

They are different routing systems from your measurement perspective.

### Enrich every responding interface

For each public IP:

```text
203.0.113.x
```

collect several independent attributes:

| Attribute | What it contributes |
|---|---|
| Prefix | Which routed block contains the interface |
| Origin ASN | Who originates that prefix in BGP |
| ASN/operator inference | Which network likely operates that interface/router |
| PTR/reverse DNS | Possible POP/router naming clues |
| GeoIP | Geographic hypothesis |
| Active latency constraints | Reject impossible location hypotheses |
| MPLS extension | Potential label/LSP evidence |
| Alias-resolution result | Whether other IPs belong to same router |

RIPE IPmap is a better conceptual model for geographic inference than relying on one database because it treats location as multi-signal evidence and uses active latency constraints. citeturn20view15

For private/shared address space, record:

```text
geo = unknown/not globally meaningful
```

rather than asking GeoIP for a city. `100.64.0.0/10`, for example, was expressly created as non-globally-routable shared provider address space. citeturn20view16

### Preserve stars instead of drawing straight lines across them

Suppose you measure:

```text
TTL 1 Stockholm
TTL 2 Stockholm
TTL 3 *
TTL 4 *
TTL 5 Frankfurt
```

The tempting visual is:

```text
Stockholm -----------------> Frankfurt
```

but that visually implies knowledge you do not possess.

A more honest representation is:

```text
Stockholm
   |
Stockholm ISP edge
   |
   ? TTL 3
   |
   ? TTL 4
   |
Frankfurt candidate
```

Or in a graphical application:

```text
known edge  ===== unknown segment =====  known edge
```

That unknown segment could represent:

```text
two ordinary silent IP hops

or

several physical routers hidden in a tunnel

or

a topology that your probe method failed to expose
```

MPLS Pipe Mode is a concrete example where multiple internal routers can intentionally collapse into a smaller visible IP-hop structure. citeturn21search0

Therefore I would **never translate a star into a guessed router coordinate**.

### Add confidence to every inference

A sensible data model might be:

```json
{
  "ttl": 7,
  "responses": [
    {
      "ip": "203.0.113.7",
      "rtt_ms": 18.7
    }
  ],
  "probe_method": "tcp-443",
  "asn": {
    "value": 12345,
    "confidence": "high"
  },
  "router_alias_id": {
    "value": "router-0081",
    "confidence": "medium"
  },
  "location": {
    "city": "Stockholm",
    "country": "SE",
    "confidence": "medium",
    "evidence": [
      "reverse-dns",
      "latency",
      "ipmap"
    ]
  },
  "mpls": null,
  "observable": true
}
```

For an unresolved hop:

```json
{
  "ttl": 8,
  "observable": false,
  "reason": "no-response",
  "location": null,
  "asn": null
}
```

And for an MPLS-like unknown section:

```text
known IP router
     |
     +---- opaque transport domain ----+
                                       |
                                 known IP router
```

This produces a much more truthful network map than placing every GeoIP result on a globe and joining the dots.

### Compare measurements over time

The correct representation should include **time**.

Routing is not a permanent path engraved into the Internet:

```text
source + destination + flow properties + routing state + time
```

determine what you observe.

Per-flow load balancing can send different flows onto different equal-cost paths, which was the central issue motivating Paris traceroute. citeturn20view4turn20view5 Anycast similarly means routing state and source location determine which service node a given address reaches. citeturn21search2

So I would timestamp every measurement and avoid combining traces hours or days apart into one supposed “actual path” without labeling them.

A useful topology system would distinguish:

```text
path observed 10:31:03
path observed 10:31:07
path observed 14:12:43

stable edges
occasional alternate edges
one-time observations
```

rather than choosing one trace as permanent truth.

## What your final mapper should—and should not—claim

The best achievable result from an ordinary Internet client is not:

> “These are the exact physical routers and cables the NYTimes packet traversed.”

You generally do not have enough information to make that claim.

A defensible result is closer to:

> “At time T, the client established this actual network flow to this endpoint. Active probes designed to preserve or approximate the flow's forwarding characteristics observed these responding interfaces at these TTLs. Those interfaces are inferred to belong to these routers/networks, with these possible geographic locations. These TTL positions were unobservable. BGP and distributed measurements are consistent with this AS-level path. MPLS/ECMP/anycast and return-path asymmetry impose the following uncertainties.”

That difference may sound semantic, but technically it is enormous.

I would rank the information in your system approximately like this:

| Observation | Confidence you can normally assign |
|---|---|
| Actual remote IP/port/protocol captured from client | **Very high** |
| A router/interface actually sent a traceroute response | **Very high** |
| Its TTL position in that measurement | **High** |
| A Paris traceroute sequence approximates one stable flow path | **High but not absolute** |
| Multiple paths discovered by MDA exist as per-flow alternatives | **High when sufficiently probed** |
| Prefix and origin-AS association | **Usually high** |
| Interface belongs to a particular physical router | **Requires alias inference** |
| Router belongs to a particular operator/AS | **Inference; often good, occasionally difficult at boundaries** |
| City/POP of a router | **Variable** |
| Exact latitude/longitude | **Often weak** |
| Exact physical fiber path | **Usually unknowable externally** |
| Hidden MPLS/tunnel interior | **Often unknowable externally** |
| Reverse route from destination to you | **Not obtainable from forward traceroute alone** |

CAIDA's need for dedicated alias-resolution and router-ownership inference illustrates why interface-to-router and router-to-network mappings are not trivial. citeturn22search1 Research on reverse traceroute likewise exists precisely because conventional traceroute cannot reveal the reverse path from a one-sided measurement. citeturn20view12

The architecture I would use for your project is therefore:

```text
                         ACTUAL APPLICATION SESSION
                                   |
                                   v
                     capture actual remote flows
                    IP + protocol + ports + time
                                   |
                +------------------+------------------+
                |                                     |
                v                                     v
           DNS evidence                         flow measurements
      A / AAAA / HTTPS etc.          Paris trace / TCP / UDP / MDA
                                                      |
                                                      v
                                             raw TTL observations
                                                      |
                         +----------------------------+----------------+
                         |                            |                |
                         v                            v                v
                    IP -> ASN                alias resolution       MPLS
                      / BGP                    IP -> router         evidence
                         |
                         v
                     AS topology
                         |
                         +--------------------+
                                              |
                                              v
                                      location inference
                               PTR + GeoIP + RTT + IPmap
                                              |
                                              v
                                    confidence-weighted graph
                                              |
                     +------------------------+----------------------+
                     |                        |                      |
                   known                    inferred               unknown
                    hops                     hops                  segments
```

That is a substantially better approximation of reality than:

```text
DNS -> GeoIP -> traceroute -> GeoIP every hop -> connect dots
```

because it deliberately separates **what you directly observed** from **what you inferred**.

The three most consequential improvements to what you are doing today are therefore:

**First, capture the destination of the real application connection instead of assuming a separate DNS lookup identifies it.** Modern clients can choose among several addresses and service endpoints. citeturn20view10turn20view11

**Second, replace ordinary traceroute as your authoritative topology source with Paris-style flow-preserving measurement plus MDA when you want the ECMP graph.** Traditional traceroute can produce false topology under per-flow load balancing; Paris traceroute and Scamper's `tracelb` were built specifically around that problem. citeturn20view5turn20view7turn20view8

**Third, stop treating IP geolocation as a physical-coordinate oracle.** Keep IP interface, inferred physical router, ASN/operator, geographic hypothesis, and confidence as separate fields. RIPE's own geolocation work uses multiple inference methods and describes location reliability as an ongoing research problem. citeturn20view15

With those changes, the `* * *` entries cease to be failures of your system. They become exactly what they are: **explicit observations that a section of the forwarding path is not externally visible using that measurement technique**. That uncertainty is part of the real Internet topology, and representing it honestly will make your map considerably more accurate than one that tries to fill every blank.
